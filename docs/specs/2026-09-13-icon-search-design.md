# 图标中英文搜索与自定义关键词设计

## 背景与范围

图标选择器目前使用少量中文映射、英文同义词扩展和 FZF 搜索，内容管理中的图标库另有名称搜索。两个入口的匹配规则不同，组合查询可能只命中部分词。自定义图标只能重命名，上传和后续编辑都缺少维护关键词的入口。

本设计先完善基于元信息的英文检索，再为同一份搜索数据增加中文翻译。内置图标的搜索数据来自名称、别名及明确关联到图标的元信息，只进行提取、规范化和等义翻译；不根据图形、经验或模型常识补充用途与同义词。

例如，元信息只有 `bell` 时，可以使用其名称并增加“铃铛”译文；如果元信息还提供 `notification` 等明确表达，才可据此加入相应的“通知”译文。元信息没有表达的叫法查不到，是检索范围的一部分。

自定义图标使用名称和用户主动填写的关键词，关键词属于用户提供的元信息。图标选择器和图标库共用检索服务，元信息处理、搜索数据维护与索引派生分别承担清楚的职责，支持后续独立调整。

## 目标与非目标

1. 基于安装包内的名称、别名及明确的逐图标元信息完善英文检索，全部定义和别名均可通过名称及完整 `prefix:name` 查找。
2. 英文名称词和上游明确列出的分类关系在构建时统一自动提取；中文翻译可以逐步补充，缺少译文不阻塞图标包升级、基础索引、构建或上线。内置图标的中文支持范围由元信息及其有效译文决定。
3. 图标选择器和图标库的逐图标搜索共用匹配、排序及数据，保留来源和图标集筛选。
4. 中文按完整关键词匹配；空格分隔的各项都必须命中。英文保留名称词及受限前缀查询。
5. 自定义图标只增加一个可选的多值“关键词”字段，上传和后续编辑均可维护，成功保存后参与搜索。
6. 保留现有 ID、别名加载、空搜索推荐、图标库浏览和分页。
7. 使用现有 PostgreSQL / PGlite 内的派生检索表，按单实例应用设计。
8. 应用启动不等待搜索索引准备。索引在后台初始化或更新，准备失败只影响非空查询；空查询推荐、图标库浏览、自定义图标管理及已有图标的展示不依赖完整搜索索引就绪。

本次不做全库中文补齐承诺、内置图标人工扩词、用途推断、自动中文分词、全局同义词扩展、状态语义分类、语义搜索、向量检索、自然语言意图理解、拼写纠错、拼音检索或运行时模型调用。移除缺少元信息依据的中英文映射和 FZF 字符子序列匹配，不在零命中后自动删词或改用部分词匹配。

不做简繁体转换或互搜；维护的内置中文翻译使用简体中文。不增加逐图标的显示名称、描述或分类编辑字段，不自动生成自定义图标关键词。现有图标集名称和描述保持原有职责。多实例协调和跨客户端实时更新不在本次范围。

自定义图标集沿用创建时的 prefix 冲突校验，图标加载沿用内置优先规则。本次不为图标包升级后与已有自定义集合重名增加专门处理。若实际冲突导致索引准备或更新失败，沿用本文的事务回滚、错误记录及搜索可用性规则，再根据实际情况修复；不增加自动隔离、迁移或专门提示。

## 方案选择

| 方案 | 收益 | 代价与取舍 |
| --- | --- | --- |
| 静态中文翻译数据加内存名称索引 | 沿用现有加载方式，省去数据库导入 | 仍需维护全量内存结构，自定义更新和图标库分页要另行衔接 |
| 同库派生索引加逐步中文翻译 | 两个入口共用查询，自定义数据与索引可同事务更新 | 增加数据库存储、首次导入及性能验证工作 |
| 独立搜索存储 | 可以隔离搜索执行队列 | 增加第二套存储、分发及自定义数据同步流程 |

选择第二种。数据库基础索引覆盖当前图标包的全量清单与明确分类关系，中文翻译逐步补充。负载实验为数据库选型提供参考，实际数据和本设计的匹配规则须按性能目标验证。

检索使用两类数据库原生索引：完整词项的 `text[] + GIN`，以及英文词的 `tsvector + GIN`。前者负责中文等完整词匹配，后者支持受限英文前缀与英文相关性排序。不引入独立搜索服务或数据库扩展。PostgreSQL 原生支持 [GIN 数组索引](https://www.postgresql.org/docs/18/indexes-types.html)和[全文检索索引](https://www.postgresql.org/docs/18/textsearch-tables.html)。

## 元信息、英文检索与中文翻译

### 全量清单与来源边界

内置数据来源为应用当前锁定版本的 `@iconify/json` 及其随包元信息。构建时直接读取全部定义、隐藏条目、别名、名称、prefix、图标集名称和 palette，并检查别名是否可以正常解析。每个 `prefix:name` 保留为独立条目，别名查询返回可直接使用的别名 ID；SVG 和别名变换由现有加载逻辑解析。

内置搜索文档的完整清单由当前图标包决定，名称沿用本文确定的归一化及分隔规则参与基础检索。这些包内字段可以直接读取，无须调用模型。分类原文和成员关系直接来自当前图标包的 categories，所有图标集采用同一提取规则；没有分类元信息的图标不补造分类。已维护的中文翻译只补充当前清单中仍有效的条目，覆盖范围允许少于当前图标包。当前包已移除的图标，即使维护文件仍保留对应记录，也不会进入搜索文档。

2026-09-06 检查的 `@iconify/json@2.2.525` 有 238 个图标集、362,866 个定义、32,698 个别名，共 395,564 个条目。后续版本以实际提取结果为准，不将固定数量写成长期校验条件。

安装包中的 Lucide、Tabler 提供名称和别名，MDI 还提供关联到具体 ID 的 categories。元信息应按实际字段提取，不为缺少字段的图标补造元信息。[Iconify 元数据](https://iconify.design/docs/types/iconify-json-metadata.html)与[图标集信息](https://iconify.design/docs/types/iconify-info.html)的层级决定其使用方式：

| 元信息 | 进入检索的方式 |
| --- | --- |
| 图标名称、别名自身的名称 | 保存名称原文，即完整 ID 中 `:` 后的部分。生成名称词时，先统一全半角和大小写，再按显式空白，以及英文或数字片段之间的 `-`、`/` 拆分；连续字母、字母与数字的组合保持完整 |
| categories 中明确列出的图标与分类关系 | 构建时遍历全部分类，自动为明确列出的成员添加分类原文，保留分类身份，作为辅助搜索数据；别名只有被明确列为成员时才获得分类信息 |
| 别名的 parent 和变换关系 | 在准备数据时核验别名能够正常加载；搜索数据按别名自身名称和显式分类关联提取 |
| 图标集名称和 prefix | 按原文作为辅助检索字段，不纳入中文翻译范围 |
| 图标集 info.tags、描述等数据 | 保留为图标集信息，不下放成逐图标内容关键词 |

名称词的提取示例：

| 名称原文 | 提取的名称词 |
| --- | --- |
| `alarm-clock-off` | `alarm`、`clock`、`off` |
| `rotate-3d` | `rotate`、`3d` |
| `usercircle` | `usercircle` |

名称原文用于完整名称匹配，拆出的名称词用于按词搜索。名称词提取不包含连写词识别、缩写展开或同义词补充。

例如，分类 `Account / User` 只关联元信息列出的图标；不能据此为其他图标添加 `account` 或 `user`。同词出现在其他图标名称时，仍可按名称命中；分类关联不成为全局筛选条件。元信息没有 `notification` 的 `bell` 条目不能凭常识添加该词。没有元信息依据的中英文映射不进入索引或查询扩展。

本次不抓取额外上游仓库、不根据 SVG 识别含义、不生成独立的内置关键词库，也不手工重复维护可以从当前图标包直接得到的英文词项或分类成员名单。新增元信息来源属于后续可独立定义的工作。

### 先完成英文检索

英文阶段使用当前图标包的完整基础清单，并自动提取全部明确的分类关系及原文，完成名称、完整 ID、名称词及实际收录的辅助字段检索，统一两个入口的多词 AND、前缀、排序及分页。完善体验的工作集中在正确提取与匹配元信息，不以补齐所有英文叫法为目标。

在准备中文翻译前，用具有明确元信息的用例验证英文行为：名称词能够命中对应条目；组合查询要求各项命中；分类词只关联声明的成员；没有元信息依据的用途词不作为该图标的命中预期。英文检索正确性不依赖中文数据。

### 中文来自同一份搜索数据

中文记录关联已经进入英文检索的源词或短语，包括完整名称、按规则得到的名称词和逐图标分类。翻译保持元信息表达的对象、动作、方向和状态，不增加其没有表达的用途、同义词或背景知识。图标 ID、prefix 和不能确定中文表达的专有名称保留原值，不强求译名。

| 元信息 | 允许的中文表达 | 检索边界 |
| --- | --- | --- |
| 名称 `bell` | 铃铛 | 不由此补充“通知”“提醒” |
| 名称词 `notification` | 通知 | 只用于该源词明确关联的条目 |
| 显式分类 `Account / User` | 分类原文及其词项的对应译文，如“账户”“用户” | 只用于分类中列出的 ID，保持辅助字段身份 |

每条翻译记录只保存归属、英文原文和中文译文。归属为图标 ID，或图标集中的一个分类（prefix 与分类名）。例如：图标 `lucide:bell`，原文 `bell`，译文“铃铛”。同一个英文词可以在不同归属下采用不同译法，不按原文自动合并为全局翻译。

图标译文的原文必须对应其完整名称或按规则提取的名称词；分类译文的原文必须对应该分类或其词项。程序根据归属和原文区分名称、名称词及分类，分类译文保持辅助检索身份。

分类译文结合所属图标集及明确成员校对语境，例如搬家分类的 `Moving` 译为“搬家”，洗涤标识中的 `Professional Care` 译为“专业洗护”。分类中的并列概念用空格分隔，沿用完整中文词及多词 AND 规则；空分类名不生成译文，专名按实际含义保留原文。

中文译文必须等义表达所记录的英文原文，不因原文存在就允许任意补词。译文无需满足自定义关键词的 20 项、40 字符输入限制，源文和译文不能因该用户输入上限被截断。

翻译可以分批维护。缺少译文或无法确认译法时，该元信息继续参与原文检索。本次维护范围为当前锁定的 `@iconify/json` 中全部已注册图标集，完成其中可依据元信息确认的名称、名称词和分类翻译。分类译文按图标集与分类归属维护，自动应用于当前包明确列出的全部成员。不设置全库或逐图标集的最低覆盖率，也不要求先补齐所有英文叫法；实际有效译文数量、中文覆盖及未译明细通过项目外的临时报告交付。

### 搜索数据维护

英文名称词和分类关系由构建程序直接提取，不使用模型。中文翻译属于开发维护阶段的独立任务，可以在明确的输入范围内使用模型。具体工具和模型由用户在实施阶段指定，本设计不绑定产品、模型、委派方式或固定批次大小。处理和翻译只依据已有元信息，不生成没有来源的检索词。

先完成英文自动提取和匹配验证，再对已确认的原文开展翻译。译文经检查、校对后保存到仓库，作为后续构建及索引生成的输入。

每次维护按以下流程交付：

1. 以现有搜索数据文件为基础，确定本次需要新增、修改或删除的内容。每次维护只处理本次范围，不要求文件覆盖全部图标；完整名称和 ID 清单由构建直接读取当前图标包。
2. 完成必要的元信息处理、翻译和校对。翻译输入包含图标或分类、英文原文及已有元信息；歧义无法由元信息消除时保留待处理。保留英文的决定须结合具体归属复核，不能仅由词表未命中得到；已有中文的名称也须检查剩余英文和版本、型号、样式是否遗漏。
3. 检查数据格式、重复、归属是否存在及英文原文是否来自其元信息；核对处理结果和译文是否忠实于来源。
4. 合并确认后的结果，更新整体搜索数据版本，记录本次范围及检查结果。其余内容继续保留，未确认的译文不进入有效中文产物。

例如，补充 100 个图标的中文翻译时，只修改对应内容；发布时提供当前图标包的完整基础记录及全部仍有效的已维护数据。没有译文的图标保留包内名称、完整 ID 和实际分类原文检索，后续再按需要补充译文。

图标包可以独立于搜索数据维护升级。构建统一按“读取当前包的全部定义和别名 → 合入有效的已维护数据 → 生成完整搜索文档”执行。仓库中的中文翻译完全未变时，新增图标仍会进入清单，先支持名称和完整 ID 检索；已移除的图标自然不进入产物。已维护记录按当前元信息检查归属、原文及关联关系，有效内容继续使用，失效内容列出并暂不使用。

维护者可根据新增、删除和元信息变化的范围，后续补充或修正译文。译法是否需要调整按需校对，不因图标包版本变化自动重新执行全库处理或翻译任务。

一次维护不要求清空其他待处理项，不重复全库语义复核。发现错误时，由维护者校对和修正相关记录；模型结果经确认后合入文件，并随应用发布。

### 搜索数据与索引的职责边界

原始元信息、已保存的搜索数据和数据库派生文档分别承担以下职责：

1. 当前图标包提供完整图标清单、原始名称及其他元信息。构建直接读取基础身份字段和全部明确分类关系，保证名称、ID 及实际分类原文按同一规则进入检索，不修改上游元信息。
2. 仓库文件只保存确认后的中文翻译及对应关系，允许只覆盖部分图标或分类。翻译通过归属和英文原文关联，可独立校对和更新；文件未覆盖某个图标不影响其包内名称和 ID 进入基础索引。
3. 文档派生合并当前图标包的基础字段与已保存且仍有效的搜索数据，完成归一化、去重、字段权重及索引格式转换；搜索服务负责匹配、排序和分页。自定义图标的名称与关键词以业务数据库为准。

数据库搜索索引可以从当前图标包、仓库中已保存的搜索数据和自定义业务记录重新生成。翻译成果须保存，恢复索引直接使用当前图标包和这些译文，缺失译文的部分采用包内名称、ID 和实际分类原文所提供的检索能力，不依赖重新执行模型任务。

搜索数据区分元信息原文、译文和用户关键词，将来接入更丰富的元信息或人工维护词汇时，可增加相应输入并明确使用规则。搜索数据与索引分离、简单的翻译对应关系和整体版本用于本次更新和校对；本次只接入元信息及其翻译，并接入用户填写的自定义关键词。

不为扩展空间增加插件系统、通用工作流引擎、未启用的生成服务或额外用户字段。后续数据来源或检索策略变化时，再明确其启用规则和验收范围。

### 搜索数据的保存与发布

仓库在 `apps/server/resources/icon-search/` 保存确认后的中文翻译及整体版本 manifest，全部纳入 Git。搜索数据使用未压缩的 JSONL 文本，按图标集拆分、稳定排序，便于逐行比较和合并，不存 SVG：

- 名称词、显式分类关系、完整 ID、名称及筛选和响应所需的基础字段都从当前图标包自动提取，不保存重复的 english 维护文件。
- 翻译记录按归属及英文原文排序，每条保存归属、英文原文和中文译文。
- manifest 统一记录格式版本、维护时使用的图标包版本、搜索数据版本、文件清单及文件校验和，不在每条记录中重复版本信息。维护时的图标包版本允许滞后；仅版本不同不判定记录失效，构建按当前图标包逐项检查对应关系。

已维护的搜索数据随应用版本一起发布。构建工具先从当前图标包读取完整基础清单，再合入仓库中已保存且仍有效的译文，完成校验及确定性的文档派生。每次产物均包含当前清单的完整搜索文档，以按图标集拆分的压缩 JSONL 文档及运行时 manifest 分发。压缩只在构建阶段进行；压缩 JSONL 和运行时 manifest 作为构建产物随应用分发，不纳入 Git，可从当前图标包和仓库文件重新生成。构建读取包内字段和分类成员关系并执行已定义的文本规则，不重新生成译文。

运行时 manifest 记录整体索引版本、稳定序列化文档的内容指纹、定义与别名数量、有效翻译数量、具有中文检索词的条目数及产物文件校验和。内容指纹包含按图标集与 ID 排序的完整派生文档，不因压缩改变；文件校验和用于检查分发文件是否完整，读取全部文档后再次核对内容指纹。

整体索引版本由应用实际使用的图标包版本、已维护的搜索数据版本、检索规则版本及文档内容指纹共同确定。图标包升级时，即使维护文件完全未变，整体索引版本也会变化。维护者仍更新可读的搜索数据版本，但遗漏该步骤时，有效译文等派生内容变化仍会自动触发索引更新。检索规则版本涵盖归一化、文档派生、索引结构，并自动纳入实际参与排序的图标集偏好配置；规则或偏好变化时同步重新派生自定义文档。程序根据这些版本判断是否复用或更新数据库索引，索引格式变化不要求重新处理和翻译已有内容。

数据库索引只保留检索、排序和响应所需内容，不向前端增加翻译维护字段。

| 情况 | 处理 |
| --- | --- |
| 当前图标包新增图标或词项，尚无对应的译文 | 正常生成基础记录，名称和完整 ID 可检索，不等待维护数据补齐 |
| 维护文件记录的图标包版本与当前版本不同 | 按当前元信息检查已有记录；有效内容继续使用，仅版本不同不阻止构建 |
| 已维护记录的图标或分类不存在，或英文原文、分类关联在当前元信息中失效 | 列出该记录并暂不使用；仍存在的图标保留基础检索，已删除图标不进入产物 |
| 数据格式非法、重复冲突，或 manifest 声明的文件缺失、损坏 | 构建明确失败，修正文件后重新构建；某个图标没有维护记录不属于文件损坏 |
| 运行时产物缺失、损坏或与程序要求不兼容 | 本次索引准备或更新失败，应用继续运行；已有可用索引继续使用，没有可用索引则提示搜索暂不可用 |

程序核对生成的基础清单是否覆盖当前图标包，并检查已维护记录的结构、归属、原文和关联关系；不要求维护文件的覆盖范围与图标包清单一致。内容是否忠实于来源在维护阶段校对，构建不执行模型判断。开发环境同样从当前图标包和已保存数据准备本地产物，发布构建将产物随 `dist` 分发。安装、构建和启动不调用模型，也不等待未完成的数据维护任务；运行时缺少产物时按索引准备失败处理。

构建按图标集生成并立即写出产物，释放该集合的派生文档。运行时通过异步解压流逐行读取和校验 JSONL，以有限批次写入 staging，不收集全量文档数组。全部文件校验和、字节数、条目数及整体内容指纹核验成功后才发布；流中途失败时清理 staging 并保留已提交索引。全量搜索文档和 SVG 不作为 JavaScript 常驻搜索数组。

## 统一检索规则

### 归一化与匹配单位

从包内名称及已保存的内置搜索数据派生文档、派生自定义文档和处理查询共用一个服务端文本模块：

1. Unicode NFKC 统一全半角，英文转小写，去除首尾空白并折叠连续空白。
2. 按显式空白分隔查询和数据中的词语。连续中文以及紧连的中英混合内容保持完整，不自动切分中文，也不在中文短语内部做子串匹配。
3. 英文或数字片段之间的连字符、斜杠按显式词项边界处理；相同处理用于名称、元信息短语、查询和自定义关键词。数字与字母紧连的词项保持完整。
4. 去重词项，保留名称、分类等字段类型；同时保存归一化的完整名称、完整名称译文和每个自定义关键词，用于精确匹配排序。

例如 `alarm-clock` 可通过 `alarm` 或 `alarm clock` 搜索，分类 `Account / User` 产生 `account` 和 `user`；`3d` 保持为一个词项。`用户管理` 不自动拆成“用户”和“管理”，`用户 管理` 则是两个显式词项。两种中文输入分别按实际存在的译文或自定义关键词匹配，不为兼容输入而自动补造词语。

只有标点、没有字母、数字或汉字等有效文本的片段不构成词项。中文短语中的标点不作为自动分词依据。归一化后为空白的查询保留原有空搜索行为；非空输入没有有效词项时返回空结果。

文本处理规则变化时更新检索规则版本，并在后台重新生成派生索引。索引格式变化不要求重新处理或翻译已保存的搜索数据；自定义关键词保留用户原文。

### 查询规则

普通关键词查询最多 120 个字符，两个入口使用同一上限。完整合法 ID 单独识别和校验，长度范围覆盖现有合法的 prefix 与 name，不被普通关键词上限截断；当前自定义 ID 的两部分各最多 256 个字符。完整 `prefix:name` 经统一全半角和大小写处理后精确查询，只返回该项或空结果，仍须满足当前来源和 prefix 筛选。

其他查询中全部词项以 AND 连接，不截断后面的词，不删词重试：

- 中文、数字、单个英文字母和中英紧连词项使用完整词匹配。
- 纯英文字母且长度至少为 2 的词项支持完整词及前缀匹配；不做英文词干或复数扩展。
- 中英混合查询同时满足全部中文完整词和英文完整词/前缀条件。
- 用户输入作为数据处理，不解释成数据库全文检索运算符。

`cam` 可以命中 `camera`，`cmr` 不能命中 `camera`。`眼睛 不可见` 要求同一条目包含两个匹配词项，不要求它们来自同一个关键词。

以用户填写关键词的自定义图标为例：假设名称和辅助字段不含这些中文词，关键词为 `["眼睛", "不可见"]`：

| 查询 | 结果 | 原因 |
| --- | --- | --- |
| 眼睛 | 命中 | 已维护完整词 |
| 不可见 | 命中 | 已维护完整词 |
| 可见 | 不命中 | 不是“不可见”的完整词 |
| 眼睛 不可见 | 命中 | 两项均已维护 |
| 隐藏 | 不命中 | 没有维护这一叫法 |

这里没有否定词解析或相反状态识别。如果用户另行填写“可见”，对应查询就会命中；搜索不推断或修正用户提供的含义。内置译文采用相同的完整词规则，但只能由其元信息产生。

### 数据库匹配与排序

文档的完整词项数组包含有效元信息、其译文及用户填写的自定义关键词按上述规则得到的词项。中文等需要完整匹配的查询通过数组包含条件检索。纯英文字母词项另行进入使用显式 `simple` 配置的向量，英文查询通过 AND 连接的受控 tsquery 检索，单字母不附加前缀运算符；两类条件同时存在时也取 AND。完整词项数组同时用于区分英文完整命中与前缀命中。

数组包含遵循[完整元素匹配](https://www.postgresql.org/docs/18/functions-array.html)，英文前缀使用数据库的[全文检索前缀能力](https://www.postgresql.org/docs/18/datatype-textsearch.html)。不依赖数据库自动解析中文词界。

先限定来源和 prefix，再对全部匹配候选排序，最后取 limit 或一页结果；不能先按字母截断自定义候选。

排序依次为：

1. 匹配层级：完整图标名称、完整名称译文或单个自定义关键词精确命中；全部查询词项完整命中；需要英文前缀扩展才能全部命中。分类及其译文只参加词项匹配，不获得名称精确命中的优先级。
2. 含汉字的查询词项在主要字段中完整命中的数量降序。每个去重后的查询词项最多计一次，不改变候选集合或匹配层级，不做中文语义评分；没有含汉字词项时此项为 0，英文查询顺序保持原规则。
3. 英文部分的 `ts_rank` 分数降序；没有英文检索条件时此项为 0。
4. 沿用现有图标集偏好，包括 Lucide、Tabler、Heroicons、Phosphor、Material Symbols 等既有顺序与低优先级集合。
5. 完整图标 ID 按稳定字节序升序。

精确短语只比较单个名称、完整名称译文或自定义关键词，不拼接不同字段制造精确命中。名称及其词项、对应译文和自定义关键词属于主要搜索字段；显式分类及其译文、图标集名称和 prefix 属于辅助字段。英文向量中主要字段使用 A 权重，辅助字段使用 B 权重。

同一英文词项只保留一次并采用最高字段权重，`ts_rank` 使用默认权重数组和 normalization = 0，避免重复词提高分数。图标集偏好不盖过更高的匹配层级或分数。

### 两个入口与分页

`GET /api/icons/search` 保持现有成功响应形状，默认 60 项、最多 100 项。空查询按原推荐清单和现有图标加载路径返回推荐图标，不依赖搜索索引；有查询时通过统一搜索索引搜索内置和有效自定义图标。

图标库的内置和自定义 tab 分别限定来源，支持可选 prefix 和游标，默认每页 80 项。空查询直接读取当前内置图标包或有效自定义业务记录，按完整 ID 的稳定字节序浏览，内置只列图标定义、排除别名。空查询始终采用上述数据来源，不依赖搜索索引是否就绪；索引准备中或准备失败时，用户仍可浏览，并从列表编辑、删除自定义图标。

两个 tab 的非空查询采用统一搜索规则。别名和图标定义采用相同的匹配、排序规则，命中后返回各自的完整 ID。图标集列表自身的名称筛选不扩大为逐图标搜索。确定本页结果后，才按既有方式取 SVG，检索表不复制 SVG。

游标改为版本化的不透明值：

- 保留完整排序元组及数据库分数精度，包含主要字段命中数量，翻页条件与排序一致。排序维度改变时同步升级规则及游标版本。
- 绑定浏览或搜索模式、归一化查询、来源、prefix 和排序规则版本，最多 2,048 个字符。非空查询另绑定整体索引版本，内置空查询另绑定当前图标包版本；自定义空查询不绑定搜索索引版本。整体索引版本不随每次自定义编辑递增，搜索索引准备或更新不使空查询浏览游标失效。
- 格式无效或与请求、规则及当前模式绑定的版本不匹配时，返回 400 和 `INVALID_ICON_CURSOR`；前端只针对该错误清除分页缓存，从第一页重新获取。
- 查询、tab、prefix 改变，或当前客户端成功修改有关自定义数据后，重置相关分页缓存。

数据不变时保证稳定翻页、无重复和遗漏。不提供跨数据修改的分页快照，也不检测其他客户端的修改；修改期间连续翻页可能重复或遗漏，刷新后获取当前结果，不为跨客户端的数据变化增加全局修改计数、轮询或推送。

## 数据库与生命周期

### 数据职责

`custom_icon_set_icons` 增加非空 `keywords: text[]`，默认 `[]`，作为自定义关键词的权威数据。现有记录迁移为空数组，不生成中文翻译。

新增可重建的 `icon_search_documents`：

| 数据 | 用途 |
| --- | --- |
| 完整 ID、prefix、name | 保留身份，ID 为主键 |
| source（内置/自定义）、图标集名称、palette | 筛选和现有响应字段 |
| customIconId（UUID，可空） | 保存 `custom_icon_set_icons.id` 的值；仅自定义图标填写，内置图标为 null，用于同步业务记录与搜索记录 |
| 归一化完整名称、完整名称译文及自定义关键词 | 判断精确匹配层级 |
| 完整词项数组 | 中文等词项匹配及完整命中判断，建立 GIN 索引 |
| 主要字段词项数组 | 对已匹配候选计算含汉字查询词项在主要字段中的完整命中数量，仅用于同层排序 |
| 英文检索向量 | 英文前缀和英文分数，建立 GIN 索引 |

例如，自定义图标从 `my:logo` 重命名为 `my:brand-logo` 时，搜索记录的完整图标 ID 随名称变化，`customIconId` 保持为同一个业务记录 UUID。

另外建立适合来源、prefix、ID 筛选的普通索引。空查询浏览从图标包或自定义业务表读取，派生表不为浏览额外保存别名标记。SVG 留在现有内置资源和自定义业务表中。

一条索引状态记录保存已提交的整体索引版本、导入数量和完成时间。状态与文档同事务提交，用于判断索引是否可用、是否需要更新，不承担每次自定义变更通知。

### 单实例后台初始化与更新

数据库迁移完成后，应用按正常流程启动定时任务、操作日志运行时和 HTTP 监听，不等待图标搜索索引准备。索引检查与导入在应用启动后的后台任务中完成。

已完整提交的索引，在图标包版本和检索规则版本与当前程序一致时可继续使用。仅搜索数据版本待更新不影响已有索引的可用性。非空查询及其分页使用当前已提交的索引版本，后台更新成功后切换到提交完成的版本。以下搜索状态只影响非空查询，空查询推荐、浏览及自定义管理继续可用。

| 场景 | 后台处理 | 搜索表现 |
| --- | --- | --- |
| 首次建立索引，没有已提交的完整索引 | 从分发文件导入内置文档，并从业务数据库回填有效自定义图标 | 显示“图标搜索正在准备”，完成后自动可用 |
| 已提交的整体索引版本与目标一致 | 直接复用 | 使用已有索引 |
| 只有搜索数据版本变化，已有索引可用 | 从分发文件整体替换内置搜索记录，保留自定义记录 | 继续使用已有索引，成功后使用更新结果 |
| 图标包版本变化，已有索引不可用 | 使用按当前图标包生成的完整分发文件整体替换内置搜索记录，不等待英文词项或译文补齐 | 非空查询显示准备状态，完成后搜索反映当前包清单的新增和移除；空查询浏览直接反映当前包清单 |
| 检索规则版本变化，已有索引不可用 | 从分发文件更新内置文档，并重新派生自定义文档 | 显示准备状态，完成后自动可用 |

内置文档分批导入 staging，最终文档和索引状态在短事务内核对并提交，对外只使用完整提交的索引。首次回填和检索规则变化时，自定义文档须与已提交的业务记录一致，避免后台回填覆盖并发编辑或恢复已删除的图标。仅内置搜索数据更新时，不修改自定义业务记录和搜索文档。

准备或更新失败时回滚，保留已提交的数据并记录错误，应用继续运行。有可用索引就继续提供搜索；没有可用索引时，搜索区域提示暂不可用。索引任务失败不关闭业务数据库或终止进程。

首次准备期间，非空搜索请求需要明确区分“正在准备”、准备失败后的“暂不可用”和正常零命中，不能用成功的空结果代替状态。两个入口在准备完成后自动重新获取当前非空查询；清空查询立即恢复推荐或浏览。已有图标的展示继续通过现有加载路径工作。

后台执行不保证数据库资源完全不受影响。实施时验证导入期间的业务响应，确实明显影响核心功能时再考虑分批等优化，不预设分批要求或批次大小。

图标包清单发生变化时，即使中文翻译文件未更新，应用仍在后台按完整分发文件整体替换内置搜索记录。提交后，新增图标可通过名称和完整 ID 查找，已移除图标的内置搜索记录同时删除。自定义图标继续以业务数据库为准，内置记录替换不影响自定义记录。之后补充译文并随应用发布，通过搜索数据版本变化触发内置索引更新。

移除 FZF 内存索引和 `ICON_SEARCH_INDEX_IDLE_TTL_MS` 配置。同版本重启复用数据库索引，无须重新解析全量图标包或重新执行处理与翻译任务。

### 自定义事务同步

所有影响搜索的自定义写入与派生文档同步放在同一业务事务。仅修改图标集描述不更新搜索文档；未提供名称时也不获取搜索写锁，提供名称时在锁内比较实际新旧值。名称实际变化后，只读取 ID、名称、palette 和关键词等派生所需字段，分批同步集合文档，不读取 SVG body。仅替换 SVG body 或尺寸且 palette、关键词未变时保留已有搜索文档：

- 新增或替换 SVG：同步名称、palette 和关键词。
- 修改名称或关键词：依据业务记录 ID，通过 `customIconId` 定位并同步搜索文档；重命名移除变更前图标 ID 的检索条目，`customIconId` 保持不变。
- 删除图标或图标集：软删除业务记录，同时移除相关搜索文档。
- 修改图标集名称：同步该集合的展示字段和辅助检索词。

成功响应表示业务记录和搜索文档均已提交。上传维持逐文件结果，每个成功文件独立完成事务；单文件失败不留下半条更新，重复跳过不修改数据。

自定义写入不以完整搜索索引就绪为前提，在迁移后的派生表中与业务数据同事务写入或移除当前规则的文档。索引准备中或准备失败时，成功变更立即体现在空查询管理列表中，非空查询仍遵循索引就绪状态。后台首次回填或重建须保留这些已提交变更，单次业务事务失败仍按原规则整体回滚。

| keywords 输入 | 新图标 | 替换或编辑已有图标 |
| --- | --- | --- |
| 省略 | 保存 `[]` | 保留原值 |
| 非空数组 | 保存所给列表 | 整体替换 |
| 显式 `[]` | 保存空列表 | 清空原值 |

## 自定义关键词接口与交互

### 字段

“关键词”为用户主动提供的可选多值输入，允许中文、英文或混合的词与短语，不要求先填写英文或提供翻译关系。最多 20 项，每项去除首尾空白后 1–40 个字符；拒绝没有有效文本的标点串，允许空列表。系统不为自定义图标自动补词或翻译。

存储保留去除首尾空白的可读原文。按统一归一化结果去重，保留首次输入，不让用户分别维护大小写和全半角重复项。字段上限、Zod schema 和请求/响应类型放在 `packages/contracts`；服务端检索词派生留在搜索模块，不进入客户端契约包。

### 上传

`POST /api/content/icon-sets/custom/:prefix/icons` 保留 `files` 和 `duplicateStrategy`，增加可选 multipart `metadata`，内容为 JSON 数组。每项是可省略 keywords 的对象，与请求文件严格按位置一一对应。

metadata 整体省略表示各文件均未提供关键词；提供时数组长度与文件数必须一致，结构在写入前校验，非法返回 400。按位置关联，不以文件名为键，避免同名文件的关键词混用。

上传抽屉沿用项目的 `NForm` / `NFormItem` 布局，依次展示目标图标集、重复处理和 SVG 文件。添加按钮与文件列表归入同一个文件表单项；列表每行包含 SVG 预览、文件名、大小、关键词和处理状态。关键词默认收起，按需展开编辑，校验错误使用 `NFormItem` 的标准反馈，上传失败原因留在对应文件行。

未编辑时省略 keywords，填写列表提交新值，“清空关键词”提交 `[]`，“恢复默认”重新省略 keywords。清空后的空态与从未添加关键词一致，显示“未设置关键词”。删减列表或重新选择失败文件时，其余文件或重新选择项的关键词随前端稳定文件 ID 保留，提交时按本次文件顺序序列化。

上传响应统一为 `results` 数组，与请求文件严格按位置一一对应，长度相同，不按文件名关联。每项通过 status 区分 `created`、`replaced`、`skipped`、`failed`：新增和替换返回含 keywords 的 icon，跳过返回名称和重复原因，失败返回具体错误信息。保留现有文件体积限制。

全局重复策略默认为跳过，可改为替换；每次提交只处理待上传项。上传期间锁定文件、关键词、重复策略和关闭操作。结果直接显示在原文件行，成功项保留为只读结果，不自动关闭抽屉，也不再次提交；跳过项可单独“替换此项”，失败项可“重新选择”文件并保留关键词，恢复待上传状态。上传后可继续添加文件，无待上传项时以“完成”结束本次操作。文件列表下方汇总新增、替换、跳过和失败数量；抽屉底部只放右对齐的操作按钮，移除无条件成功提示。

请求整体失败时显示错误并保留可重试的文件与关键词，不将未确认结果标记为成功；考虑到此前文件可能已独立提交，刷新相关缓存。关闭抽屉或切换图标集后，旧请求仍可刷新缓存，但不得覆盖新一轮抽屉的文件和结果。

### 编辑

“重命名图标”改为“编辑图标”，使用独立编辑抽屉，沿用项目的 TanStack Form 与 `NForm` / `NFormItem`，包含名称和可选关键词，支持查看、增删和清空。字段间距、字段下方的校验反馈及底部取消、保存按钮与其他编辑抽屉一致；关闭时接入现有的未保存修改提醒。重新打开后以所选图标重新初始化，旧保存请求不得关闭新抽屉或覆盖新表单，成功写入仍刷新相关缓存。

`PATCH /api/content/icon-sets/custom/:prefix/icons/:name` 接受可选 name 和 keywords，至少提供一项，兼容仅 name 的请求。只改关键词不改变 ID。

自定义图标列表、上传成功项和编辑响应返回 keywords，空值统一为 `[]`；选择器搜索响应不增加关键词或 SVG。

沿用现有权限。编辑操作记录为 `content:icon:update`，更新对应操作类型和中文标签；已记录的 `content:icon:rename` 操作保持可识别，不能把仅改关键词的操作记录为重命名。

### 缓存与提示

当前客户端成功上传、替换、编辑、删除或修改相关图标集信息后，失效受影响的列表、图标集和选择器搜索缓存，重新获取当前结果。上传部分失败但有成功新增或替换项时也执行失效。

选择器和图标列表共享关键词防抖逻辑，分别保留 200ms 和 250ms 延迟，清空输入立即恢复推荐或浏览。输入框保留原文，请求只去除首尾空白；通过共享查询契约校验的输入按统一归一化结果复用缓存，未通过校验的输入独立使用原文缓存键，避免 NFKC 展开后长度不同的有效与无效请求混用结果。

两个入口说明支持中英文名称和关键词，并提示“部分内置图标支持中文，可尝试英文名称或图标 ID”。非空查询在没有可用索引且后台准备中时显示“图标搜索正在准备”，准备完成后自动恢复当前查询；准备失败且没有可用索引时显示“图标搜索暂不可用”。清空查询后恢复推荐或浏览，不用搜索状态遮挡列表和管理操作。已有可用索引的后台更新沿用正常搜索界面。

准备状态以 1、2、4、8 秒为上限逐步退避重试，每次随机采用上限的 80%–100%，等待前次请求结束后再计时；页面隐藏、入口关闭或切换到非活动 tab 时暂停，恢复可见且入口仍活动时继续。离开准备状态后重置退避次数。暂不可用状态不自动轮询，提供“重试”按钮重新获取当前查询；按钮不触发服务端重建任务。

索引就绪后的零命中可提示“未找到匹配图标，可尝试英文名称、图标 ID 或其他关键词”；请求失败保持错误状态。准备状态和失败状态不显示零命中文案。保留现有防抖、分页加载和 SVG 渲染。

Iconify JSON 导出维持现有标准结构，不添加私有 keywords；本次不新增关键词导入/导出功能。

## 验收与验证

### 数据与检索质量

- **基础清单完整、检索词有来源**：生成的基础清单与当前 Iconify 包一致，定义和别名无遗漏、重复、未知 ID 或无法解析的条目，全部名称和完整 ID 可检索。名称按固定规则参与检索，全部明确分类关系直接取自当前包；不要求译文覆盖全部图标，没有分类的图标不要求补分类。
- **先验证英文行为**：使用无中文译文的数据验证名称、完整 ID、组合查询、前缀、排序和分页。分类只匹配源字段声明的成员，图标集 tags 不被当作逐图标内容词。
- **翻译对应明确且等义**：检查翻译记录的归属和英文原文是否存在，对本批新增或修改的译文校对是否等义、是否加入原文没有的含义。没有译文的条目不判失败。
- **检索预期有明确依据**：内置查询的预期来自源元信息及有效译文，自定义查询的预期来自名称及用户关键词。验证命中和排序，不要求元信息未表达的用途、任意同义词或自然句子命中。
- **覆盖如实记录**：通过项目外的临时报告交付基础条目数、有效翻译数、具有中文检索词的条目数、本批范围及待更新数量，统计报告不纳入 Git；不设置全库翻译覆盖率、逐图标集抽检配额或任意自然表达通过率门槛。
- **真实中文流程可用**：首批译文能进入分发产物、数据库和两个搜索入口；分类译文保持辅助身份。缺失或失效译文不影响对应英文/ID 检索。模拟汉字只能用于负载探针，不能证明翻译质量。

### 必要行为验证

1. 两个入口的非空查询在相同来源和 prefix 下有一致候选及排序；筛选在 limit 前生效，推荐保持既有行为。图标库空查询从图标包或业务记录浏览，排除内置别名；非空查询中别名身份不影响匹配和排序，别名命中返回自身 ID。
2. 全词 AND、中文完整词、显式空格、英文连字符和斜杠、完整名称及其译文优先、英文两字母起前缀、单字母/数字/紧连混合词完整匹配，以及取消 FZF 子序列的行为。
3. 以用户关键词夹具验证 `["眼睛", "不可见"]` 的匹配表；以仅有 `bell` 元信息的内置夹具验证不扩充 `notification` 或“通知”，分类及其译文只进入声明的成员，不提升为名称精确匹配。
4. 大小写、全半角、无效词项、普通查询长度、合法长 ID 及别名精确查询。
5. 自定义写入同步，省略 keywords 与 `[]` 的区别，同名文件不串用，事务失败回滚；重命名后完整图标 ID 更新，`customIconId` 仍关联同一个业务记录 UUID；图标集改名和删除同步。
6. 当前客户端成功修改后缓存及时更新；数据不变时翻页无重复和遗漏，无效游标重置，跨修改翻页遵循已声明限制。搜索索引准备或更新不使空查询浏览游标失效；内置图标包变化使内置浏览游标失效。
7. 应用启动不等待首次导入或版本更新；同版本复用，搜索数据更新仅替换内置文档，必要时回填或重新派生自定义文档，并发自定义编辑和删除不被回填覆盖。
8. 后台准备中与准备失败的状态和零命中明确区分；就绪后自动恢复当前非空查询，已有可用索引在更新期间继续使用，成功提交后搜索分页采用更新后的索引版本。
9. 导入失败回滚并保留已提交索引；运行时产物缺失、损坏或不兼容不终止应用。没有可用索引时非空搜索暂不可用，已有图标仍可展示；空查询推荐、浏览和从列表编辑、删除自定义图标均可用。准备期间成功的自定义变更在浏览中立即可见，就绪后能反映到搜索结果。
10. 从当前图标包的基础字段与仓库中已保存的有效搜索数据生成分发产物，结合自定义业务记录生成数据库索引，不调用模型，不重新生成已维护的译文；发布文件包含完整基础记录和全部仍有效的已维护数据。
11. 模拟图标包同时新增和移除定义、别名，中文翻译及其来源版本均未更新：构建成功，产物清单与当前包一致。空查询浏览直接反映当前包的新增和移除定义，无需等待索引；后台整体替换后，新增条目能在两个入口通过名称和完整 ID 查找，已移除条目从内置搜索记录和搜索结果中消失。维护文件中的残留记录不能使已移除条目重新出现，自定义记录保持不变。无需调用模型或先补维护记录。
12. 已维护文件覆盖不全或来源图标包版本滞后不判失败；有效译文继续使用，归属、原文或分类关联失效的记录列出并排除。数据格式损坏或 manifest 声明文件缺失、损坏时构建明确失败。

使用小型、有业务意义的契约、服务及浏览器测试；全量清单校验、数据检查和性能测量独立运行。实现完成后执行 `pnpm check`，其中 Chromium 浏览器测试按仓库约定在沙箱外运行。

### 性能目标

以 Apple M4、10 个逻辑 CPU、24 GiB 内存、macOS arm64 的本地 PGlite 为开发验收基线，记录实际 Node.js 和 PGlite 版本。采用当前图标包的全量基础索引及包内明确分类关系及实际已维护的中文译文，以默认返回 60 项为主：

- 预热后的核心搜索每类查询 P95 不超过 50 ms，覆盖普通和宽匹配查询。
- 单实例每批 10 个请求的突发负载 P95 不超过 200 ms。

核心计时包含输入归一化、数据库执行及结果映射，不含网络、前端防抖和 SVG 渲染。分别报告英文、已收录译文的中文、混合、宽匹配及分页表现，不以混合平均值掩盖慢查询；突发测试记录负载组成和逐请求延迟。

分别记录应用开始提供服务的时间、首次或更新后的后台导入耗时、搜索就绪时间、同版本启动、磁盘占用、内存及空库/业务数据库基线。响应性探针在读取分发文件之前启动，覆盖解压、解析、staging 导入、发布及旧表清理的完整过程，同时记录采样峰值内存。测量后台导入期间核心业务请求的响应，并与未导入时比较，同时测量搜索与业务混合负载的排队影响。明显影响核心功能时再优化导入方式，不以是否分批作为验收项。实际搜索数据变化较大时重新测量，不用部分译文的数据规模推断全库翻译后的成本。

生产 PostgreSQL 在目标环境单独复测核心查询、分页和业务混合负载，记录版本、机器和连接配置。缺少目标环境时明确保留验证限制，不用 PGlite 数字替代生产结论。

2026-09-14 常用图标集阶段的开发验收约定：本机高负载下，移除中文译文的对照数据同样未达到上述延迟目标；相同环境的有、无中文对照未显示该阶段的翻译扩充造成性能劣化。用户据此确认该阶段的性能验收通过。上述目标保留，该次测量不作为延迟已达标的证据；一次性测量报告保存在临时目录。

## 负载实验与适用范围

2026-09-06 的实验使用上述 M4 环境、Node.js 24.20.0、SQLite 3.53.4 FTS5、PGlite 0.5.8（PostgreSQL 18.3 / WASM），两种引擎均索引 395,564 个条目。每个不同英文词项附加 3 个确定性汉字词项，每条平均 12.88 个词项；这些模拟词没有中文语义。

查询最多返回 60 条 ID 和分数，包含 worker 往返，不含 HTTP、SVG 和前端渲染。单查询 P95 来自两轮各 50 次预热后样本；突发 P95 来自两轮各 30 批、每批 10 请求，共 600 个样本。

| 指标 | SQLite FTS5 | PGlite 全文检索 |
| --- | ---: | ---: |
| `file` 查询 P95，5,419 项命中 | 2.60 ms | 2.59 ms |
| `outline` 查询 P95，45,532 项命中 | 20.39 ms | 23.35 ms |
| `a*` 压力查询 P95，79,631 项命中 | 47.37 ms | 44.88 ms |
| 10 请求突发 P95 | 81.50 ms | 74.82 ms |
| 一次建表、导入和索引构建 | 1.91 s | 5.88 s |
| 检索数据占用 | 119.34 MiB | 221.40 MiB |

这些数值的适用限制为：

- 实验采用单一全文检索向量，测量范围不包含完整词数组与英文向量组合，也不包含真实中文搜索质量。
- `a*` 仅是宽匹配压力探针，产品不开放单字母前缀。突发测试每批完成后才发下一批，不代表持续流量的饱和容量。
- 构建各测一次，未含引擎初始化和源数据提取；SQLite 使用默认 FULL 同步，PGlite 使用默认 `fsync=off`，不能外推生产 PostgreSQL 写入成本。
- SQLite 占用是索引文件；PGlite 是图标表、TOAST 和索引，不含系统目录与 WAL。空 PGlite 进程 RSS 已约 912–914 MiB，不能当作图标索引增量。
- 人工排队探针每批先发 8 个搜索，再发 2 个业务点查：共用 PGlite worker 时点查 P95 为 94.18 ms，搜索独立使用 SQLite worker 时为 0.60 ms。该差异提示开发环境需关注排队，不代表原生 PostgreSQL 的多连接表现。
- 原生 PostgreSQL 性能不在该实验的测量范围内，需按实际数据和性能目标单独验证。
